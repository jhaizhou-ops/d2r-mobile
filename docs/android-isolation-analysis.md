# 我们的代码怎么和上游隔开——大白话版

> 写作约定：本仓库文档一律用大白话；中文不好说的词直接用英文（比如 git conflict、merge）。
> 本文回答一个问题：**怎么别再让上游更新跟我们打架。**

## 一句话总结

我们的改动尽量都放在"自己的新文件"里，少去动上游的老文件。现在 98 个有改动的文件里，
**63 个已经是我们自己新建的**（永远不会打架），剩下 35 个是"动了上游老文件"的——**打架只会
发生在这 35 个里**。做到"一个上游文件都不碰"不可能，但把这 35 个管好，就够用了。

## 为什么会打架

- 上游在做 iPhone 版，一直更新他们的代码。
- 我们在做 Android 版，也改了很多地方。
- 如果两边**改了同一个文件的同一片区域**，git 就不知道该听谁的，就需要人工解决（conflict）。
- 不是假设：这次拉上游的 5 个新提交，真撞了 2 个冲突，都在 `hle.c` 和 `loader.c` 里。

## 现状：98 个文件分两种

**第一种：我们自己新建的文件（63 个）** —— 上游永远不碰，不打架。
比如 `dm/android/` 里的 33 个、Vulkan 图形后端 `nvn_vk.c` 那一整套。
**以后写新代码，继续优先放这里。** 这是目前的主流做法。

**第二种：上游的老文件，我们往里插了东西（35 个）** —— 这就是要治理的对象。

另外有个好消息：我们总共只删了上游 140 行代码——**我们几乎全是"往里加"，很少"改原来的"**。
"加"比"改"好合并得多。

## 这 35 个文件，按危险程度分四堆

### 第一堆：脚本生成的文件（1 个）——不用管

`nvn_thunks.S` 是脚本生成的（几百个转发小函数）。我们加的部分被 `#ifdef __ANDROID__ ... #else
... #endif` 包了起来：我们的在这半边，上游的在那半边，两块不挨着。git merge 基本不打架。
**保持现状。**

### 第二堆：我们插了 100 行以上的（6 个）——最危险，要动手术搬走

| 文件 | 我们加了多少 |
|---|---|
| `hle_oe.c` | 341 行 |
| `hle_fs.c` | 289 行 |
| `hle_thread.c` | 142 行 |
| `patch_nso.py` | 141 行 |
| `nvn_dirty.c` | 137 行 |
| `hle_nvn.c` | 116 行 |

**做法**：把"我们写的那段"搬到 `dm/android/` 下面的新文件里，老文件里只留几行：
"如果是 Android，就调用我们的实现"。搬完之后，上游改他们的、我们改我们的，互不干扰。
搬一个约半天，搬完一个测一个（能编过 + 手机上跑一圈不崩）。先拿 `hle_oe.c` 开刀。

### 第三堆：头文件里加了几行（5 个）——立个规矩就行

`nvn_obj.h`、`hle.h`、`dm.h` 这些文件我们只加了几行（声明、枚举值，3-9 行）。
**做法**：以后往这些文件里加东西，统一放在文件末尾一小块区域，两端标上
`ANDROID-BEGIN` / `ANDROID-END`。万一打架：直接用上游的版本，把我们那几行贴回去，一分钟解决。

⚠️ 一个特别提醒：`nvn_obj.h` 里的操作编号（`OP_xxx`）是主机程序和游戏模块共用的"暗号"。
**改编号 = 必须两端一起重新生成模块**，不然游戏直接坏。上次想同步上游那个文件跨距修复（#68）
就是碰到这个才放弃的。

### 第四堆：小改动（约 20 个）——先记着，不动

比如 `loader.c` 加了 49 行、`thread.c` 加了 19 行……全在 65 行以内。先不动它们，
记到"打架了怎么办"的清单里。以后哪个真撞了，再单独处理那一个。

## 能做到"一个上游文件都不碰"吗？

**做不到。** 原因很直白：移植这件事，天生就必须在上游的几道"接口"上挂钩子——
加载器（loader）、HLE（把 Switch 的系统调用接到 Android 上）、图形分发（同一个游戏，iPhone 走
Metal，我们走 Vulkan，得有人分岔）。钩子不挂在上游文件里，就接不上。

除非上游愿意做一套"所有平台统一插槽"（platform interface）——那是个大工程，还得他们配合，
现在不现实。**把钩子做到最少、位置固定，就是性价比最高的状态了。**

## 接下来按这个顺序做

1. **清单（已完成）**：35 个文件，每个写一行"打架了怎么办"（见文末表格）。
2. **搬第二堆的 6 个大文件**：每个约半天；搬一个、测一个。最危险的部分就没有了。
3. **（可选，以后）**：把第一堆那个生成文件也拆开；再写个小脚本 `sync_upstream.sh`，
   以后每次拉上游更新，它自动告诉你"哪几个文件可能打架、每个文件该按哪条规矩处理"。
