# 我们的代码怎么和上游隔开——大白话版

> 写作约定：本仓库文档一律用大白话；中文不好说的词直接用英文（比如 git conflict、merge）。
> 本文回答一个问题：**怎么别再让上游更新跟我们打架。**

## 一句话总结

我们的改动尽量都放在"自己的新文件"里，少去动上游的老文件。现在 98 个有改动的文件里，
**63 个已经是我们自己新建的**（永远不会打架），剩下 35 个是"动了上游老文件"的——**打架只会
发生在这 35 个里**。做到"一个上游文件都不碰"不可能，但把这 35 个管好，就够用了。

## 函数级改动的决策表（"要不要给 Android 做个专属函数？"）

当我们和上游都要改同一个函数时，先回答一个问题：**这个差异，是"平台机制不同"，还是"同一个
功能、两边的做法不同"？**

| 情况 | 判断标准 | 正确做法 | 我们树里的例子 |
|---|---|---|---|
| **① 平台机制不同** | 不 fork 根本做不了：两边的 OS 接口/机制真的不一样 | **双分支双实现**：`#ifdef __ANDROID__` 走我们的、`#else` 上游原样 | 目录原子交换（Apple `clonefile`/`renamex_np` vs Linux `renameat2`）；mprotect 计时（mach 时钟 vs 我们的时钟函数）；`resolve_import` 的符号段定位（Mach-O 段 vs 链接器符号）；运行模式默认值 |
| **② 同一功能、做法不同** | 逻辑与平台无关，只是两边各自实现、风格不同 | **合流**：改成跟上游一样的形态（语义等价时首选；实在合不了才登记） | `resolve_import` 的"弱导入保持 NULL"（2026-10-17 已合流） |
| **③ Android 独有功能** | 上游根本没有这个功能（不是平台差异，是"他们没有"） | **小钩子**：上游函数里留一两行 guarded 调用，实现在 `dm/android/`；登记 | HLE 里的 `dm_android_platform_setting`（录像/截图许可、性能档请求）；挂起时的管线缓存落盘 |

**为什么情况②千万不要 fork 成"Android 专属函数"：**

- **维护变两份**：上游以后修这个逻辑的 bug，只会修进他们的版本，我们得自己发现、自己跟；
- **`#ifdef` 给出错误暗示**：会让后来人以为"这里本来就是平台差异"，不再去合流；
- **口子一开，全局裂开**：每个双方都碰的函数都存一份 Android 影子实现 → 整个项目变成
  "平行复制品"，和"隔离"的目标恰好相反。

**"fork 成 Android 专属"唯一正确的场合 = 情况①**——这时候 fork 不是"分歧"，是"事实"：
两边的 OS 真的不同，两份实现各自都对，也永远不会（也不需要）合流。

**情况③的终局**：如果这个功能其实是通用的（不依赖 Android 特有机制），把它提 PR 给上游
（上游作者明确欢迎）；上游收了，"分歧"就永久消失。

**对照审计结果**：那 35 个文件里的双分支标记，绝大多数属于①；②的已知案例只有一个
（`resolve_import`，已合流）；③的都已经用小钩子形态（guarded 包一两行调用）。

## 硬性规矩（从现在起，非 iOS 代码的每一次迭代都必须遵守）

1. **能新建文件就新建文件**：新功能优先写在 `dm/android/` 下、或者独立的新文件里。
   （现状 98 个改动文件里 63 个是新建的——这个比例以后只许升、不许降。）
2. **必须动上游文件时**，只允许三种手法：
   - **双分支**：`#ifdef __ANDROID__ …我们的… #else …上游原样… #endif`。
     现役大文件都这么干（hle_oe.c 17 处、hle_fs.c 41 处、hle_thread.c 21 处、nvn_dirty.c 5 处、
     hle_nvn.c 19 处）。
   - **小钩子**：上游文件里只留一两行"如果是 Android，就调用我们的函数"，实现在 `dm/android/`
     的新文件里。
   - **追加区段**：头文件/枚举里加东西，必须放进标了 `ANDROID-BEGIN / ANDROID-END` 的块
     （已建：`nvn_obj.h`、`nvn_dirty.h`、`nvn_mtl.h`；新加的地方照此建块）。
     **枚举类编号严禁往中间插**——那是"主程序 + 改写后的游戏模块"两端共享的暗号。
3. **每次迭代收尾跑一遍审计脚本**：`bash dm/android/tools/sync_surface_audit.sh`。
   它会数"新建了几个文件、动了几个上游文件、每个文件是什么形态"。
   规矩：**动上游文件的数量不许悄悄涨**；涨了要在提交说明里写清楚为什么。
4. **"声明式分歧"要登记**：像 `resolve_import_optional` 这种直接改上游函数签名的（宏隔离不了），
   登记进本文档的策略表，合并时按登记的策略处理（这次就是这么处理上游 #66 的）。
5. 本文档文末的**策略表是唯一权威**：撞车先查表；处理完把表更新。

## 为什么会打架

- 上游在做 iPhone 版，一直更新他们的代码。
- 我们在做 Android 版，也改了很多地方。
- 如果两边**改了同一个文件的同一片区域**，git 就不知道该听谁的，就需要人工解决（conflict）。
- 不是假设：这次拉上游的 5 个新提交，真撞了 2 个冲突，都在 `hle.c` 和 `loader.c` 里。

## 现状：98 个文件分两种

**第一种：我们自己新建的文件（63 个）** —— 上游永远不碰，不打架。
比如 `dm/android/` 里的 33 个、Vulkan 图形后端 `nvn_vk.c` 那一整套。
**以后写新代码，继续优先放这里。** 这是目前的主流做法。

**第二种：上游的老文件，我们往里插了东西（35 个）** —— 这就是要治理的对象。

另外有个好消息：我们总共只删了上游 140 行代码——**我们几乎全是"往里加"，很少"改原来的"**。
"加"比"改"好合并得多。

## 这 35 个文件，按危险程度分四堆

### 第一堆：脚本生成的文件（1 个）——不用管

`nvn_thunks.S` 是脚本生成的（几百个转发小函数）。我们加的部分被 `#ifdef __ANDROID__ ... #else
... #endif` 包了起来：我们的在这半边，上游的在那半边，两块不挨着。git merge 基本不打架。
**保持现状。**

### 第二堆：我们插了 100 行以上的（6 个）——最危险，要动手术搬走

| 文件 | 我们加了多少 |
|---|---|
| `hle_oe.c` | 341 行 |
| `hle_fs.c` | 289 行 |
| `hle_thread.c` | 142 行 |
| `patch_nso.py` | 141 行 |
| `nvn_dirty.c` | 137 行 |
| `hle_nvn.c` | 116 行 |

**做法**：把"我们写的那段"搬到 `dm/android/` 下面的新文件里，老文件里只留几行：
"如果是 Android，就调用我们的实现"。搬完之后，上游改他们的、我们改我们的，互不干扰。
搬一个约半天，搬完一个测一个（能编过 + 手机上跑一圈不崩）。先拿 `hle_oe.c` 开刀。

### 第三堆：头文件里加了几行（5 个）——立个规矩就行

`nvn_obj.h`、`hle.h`、`dm.h` 这些文件我们只加了几行（声明、枚举值，3-9 行）。
**做法**：以后往这些文件里加东西，统一放在文件末尾一小块区域，两端标上
`ANDROID-BEGIN` / `ANDROID-END`。万一打架：直接用上游的版本，把我们那几行贴回去，一分钟解决。

⚠️ 一个特别提醒：`nvn_obj.h` 里的操作编号（`OP_xxx`）是主机程序和游戏模块共用的"暗号"。
**改编号 = 必须两端一起重新生成模块**，不然游戏直接坏。上次想同步上游那个文件跨距修复（#68）
就是碰到这个才放弃的。

### 第四堆：小改动（约 20 个）——先记着，不动

比如 `loader.c` 加了 49 行、`thread.c` 加了 19 行……全在 65 行以内。先不动它们，
记到"打架了怎么办"的清单里。以后哪个真撞了，再单独处理那一个。

## 能做到"一个上游文件都不碰"吗？

**做不到。** 原因很直白：移植这件事，天生就必须在上游的几道"接口"上挂钩子——
加载器（loader）、HLE（把 Switch 的系统调用接到 Android 上）、图形分发（同一个游戏，iPhone 走
Metal，我们走 Vulkan，得有人分岔）。钩子不挂在上游文件里，就接不上。

除非上游愿意做一套"所有平台统一插槽"（platform interface）——那是个大工程，还得他们配合，
现在不现实。**把钩子做到最少、位置固定，就是性价比最高的状态了。**

## 接下来按这个顺序做

1. **清单（已完成）**：35 个文件，每个写一行"打架了怎么办"（见文末表格）。
2. **搬第二堆的 6 个大文件**：每个约半天；搬一个、测一个。最危险的部分就没有了。
3. **（可选，以后）**：把第一堆那个生成文件也拆开；再写个小脚本 `sync_upstream.sh`，
   以后每次拉上游更新，它自动告诉你"哪几个文件可能打架、每个文件该按哪条规矩处理"。

### 删改行专项审计（2026-10-17，回答"该不该给 Android 做专属函数"）

审计对象：35 个文件里**被删/改的 141 行上游原码**（其余全部是纯新增，不涉及冲突）。
逐行核对后的最终结论：

- **绝大多数 = 守卫重包（情况①/③，合规，无需处理）**：上游原行原样移进 `#else`，Android 变体
  放进 `#ifdef __ANDROID__`。代表：`hle_net` 的离线网络策略（Android 走真实网络策略钩子）、
  `hle_time` 的返回点识别与 ABI 断言、`hle_guestthread` 的 `posix_memalign`（Bionic API 26 没有
  `aligned_alloc`）、`hle_fs` 的克隆/原子交换（Apple `clonefile`/`renamex_np` vs Linux `renameat2`）、
  `nvn_dirty` 的时钟抽象（mach vs 时钟函数）、各 HLE 里的 `dm_android_platform_setting` 上报。
- **唯一的情况②（同一功能、两边写法不同）：`resolve_import` 族 —— 已合流**（见上表）。
- **两个"上游 PR 候选"**（对我们无害、对上游也有价值——属"改进"，不是"分歧"）：
  1. `patch_nso.py` 的 4 条分辨率补丁去掉了"仅宿主"标记（4 元组 = 全目标）：语义是
     "对原版两种尺寸结果不变、对任意尺寸正确"，注释里已写明 Mac 行为不变——严格改进，择机上 PR；
  2. `nvn_dirty.c` 的查询统计/页摘要（NvnDirtySummary）是上游没有的**加性**功能；若上游觉得有价值，
     整块提 PR——提交后这份"分歧"永久消失。

**最终状态：代码无需再搬。** 按决策表重审之后，全树已是四种合规形态
（双分支 / 小钩子 / ANDROID-BEGIN 区段 / 工具内建双目标）；剩余只有两个待提 PR 的改进。
以后每次迭代：先按「硬性规矩」动手，收尾跑 `sync_surface_audit.sh` 复查。
