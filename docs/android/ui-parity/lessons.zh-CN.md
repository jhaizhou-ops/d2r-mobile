# 安卓 ↔ iOS 对齐：教训与规矩（2026-10-18）

> **这份文档是什么**：这几天做「建角 / 模式页 / 中文名 / 自动选怪 / 小地图」时踩的坑，以及由此定下的做事规矩。
> **给谁看**：接下来动安卓侧、或者动两端共享文件的人（含 AI）。
> **一句话**：**iOS 那份就是规格。改共享代码前先读上游怎么写；看不出问题就先拿读数把事实定住，别加代码去猜。**

---

## 0. 动手前的一张清单

改任何东西之前，按顺序问自己：

1. **上游 iOS 怎么做的？** —— `git show upstream/main:<文件>` 先读一遍。上游有就照上游，别自己发明。
   （「一比一对齐 iOS」是字面意思：iOS 的行为就是规格。）
2. **这个文件是共享的吗？** —— `dm/host/**`、`dm/ios/tools/*.py`、`dm/ios/Sources/dm_touch_controls.c`、
   `front.h` 都是**两端共用**（`docs/android/ui-parity/analysis.zh-CN.md` §3.2）。改它 = 改 iOS。
3. **iOS 会被我改坏吗？** —— 会的话，改成加法式平台开关，并**证明 iOS 产物逐字不变**（§2）。
4. **我是在"读状态后动作"，还是在"跟游戏抢"？** —— 见 §3。
5. **有没有读数能先证明我的假设？** —— 日志 / 诊断面板 / 截图量测，见 §4。
6. **这会不会是构建口径问题，而不是实现问题？** —— 见 §5。

## 1. 别自己发明：先看上游 iOS 怎么做

**案例（小地图）**：上游 `dm/host/dm_cursor.c` 的 `ui_map_pump` 里本来就有一句
「触屏模式在局里读到『透视地图尺寸』= 全屏(0) → 改回微缩放地图放右(2)」。

我把它当成"我们之前的旧行为"删掉了，然后自己写了三样东西：
- 「进局替玩家按一次原版地图键」（上游没有）
- 「按角色名把开关状态记到 `map_state.txt`」（上游没有）
- 「档位 `!=2` 就钉到右边」（上游是 `0 → 2`，其余档不动）

**结果**：代码越堆越多、行为越来越乱，最后**逐字回到 `upstream/main` 就对了**，剩下真正需要的只有两条
（点按命中区、安卓侧进局开地图），而且都有明确理由。

**规矩**：共享文件里已有的逻辑，先当成"故意的"来理解，别当遗留垃圾删。

## 2. 共享代码改动：加法式 + 双端可验证

改共享文件时，**iOS 的产物必须逐字不变**。"我跑不了 iOS 所以不管"不成立 —— 用 diff 证明，不需要跑 iOS。

这次用过、有效的两种证法：

| 对象 | 证法 |
|---|---|
| 生成器（Python，如 `touch_layout.py`） | 同一输入跑改动前 / 后，产物 **SHA256 比对**（改前 = 缺省路径的产物） |
| 共享 C 文件（如 `dm_cursor.c`） | `clang -E -P -U__ANDROID__` **预处理产物逐字比对**，证明 `#ifdef` 之外零变化 |

**平台开关要集中在一处**，不要散落：
- `DM_TOUCH_TWO_CARDS`（模式页只留两块方块）→ 只在 `dm/android/tools/gen_overlay.sh` 里设
- `DM_GEN_ASSETS` / `DM_NATIVE_ART_DIR` / `DM_NATIVE_ART_C`（生成物落点）→ 同上

开关默认值 = iOS 行为；Android 脚本显式打开。

## 3. 不要跟游戏自己的状态抢

**案例（"进局没地图"）**：我加了「进局看不到地图就替玩家按一次原版地图键」。它错在**时机**：

- 面板还没建起来时，读状态只会得到"关着"；这时按一下 —— 正好把游戏**正要开**的那张图按掉
- 两秒后再判、再按……于是真机表现是：进局没地图 / 点右上角半天才反应 / 地图线画出小地图框（面板被留在坏状态）
- 更糟的是每次进局都推翻玩家的选择：「我打开地图、保存、再进，还是关的」

**规矩**：
- **"读不到" ≠ "没开"**：读不到状态就等，别按。
- 动作之前先确认前置条件（这里是"面板已建起来"，与"地图开着没"是两件事）。
- 优先用游戏自己的机制（设置项、它自己的变更回调）；合成的按键输入是**最后手段**。
- 一次动作后要复验结果（按下去到画出来有一两帧延迟，别立刻下结论）。

## 4. 事实优先：先量，再改

这次真正把方向定下来的，全是**读数**，不是推理：

| 读数 | 结论 |
|---|---|
| `小地图诊断：… 可见 1 … 可见 0 … 可见 1 …` | 有东西在**反复开关**地图（不是"没画出来"） |
| `TOUCH_UI_MODE panel=0 mask=0x7ff` | 游戏态确实排除了地图键那一**位** → 排除"触摸模型发键"这个方向 |
| 截图平均亮度 49.3（小图态）vs 49.0（全屏态） | 全屏图没把世界压暗（当时以为的"透明全屏图"是这个） |
| `小地图诊断：… 配置 1 …` （新角色） | 游戏给新角色的档位是「微缩放左」，不是"右边画错了" |

**教训**：没有读数时，我的猜测连错三次（以为裁剪坏了、以为安全区在写矩形、以为游戏不给矩形）。

## 5. 两端不一致时：先查构建口径，再查实现

**案例（中文角色名）**：iOS 能用、安卓不能。根因不是实现，是**清单**：

- iOS：`dm/host/Makefile` 用 `$(sort $(wildcard hle_*.c))` 收源文件 → 加文件不用改清单
- Android：`dm/android/CMakeLists.txt` 是**逐个手写** → `hle_charname.c` 谁都没编，而且**不报错、不出声**；
  文档里还写着它已经在了，所以谁都以为编了

**现在的做法**：通配 + 排除表 + 断言（`dm/android/CMakeLists.txt`）
- 通配：不在排除表里的 `hle_*.c` 一律编进来
- 排除表：每个不编的逐条写明原因（Android 已有等价实现 / Apple 专属 / 靠 iOS 的段挂载）
- 断言：表里每一项必须是真存在的文件 —— 改名或删除后留下假条目 = 静默少编一个，正是当年的坑

**同类问题：跨树写入**。安卓构建原本会往 iOS 源码树写生成物。现在统一落 `dm/android/build/gen-assets`，
三个落点都能用环境变量覆盖，缺省仍是原位（iOS 行为不变）：
`DM_GEN_ASSETS`（原版衍生资源）、`DM_NATIVE_ART_DIR`（技能图集 PNG）、`DM_NATIVE_ART_C`（技能索引 .c）。

## 6. 「场景名 = 地图开关」这个坑（值得单独记）

右上角那一格上有**三层**东西叠着：

1. **游戏自己右上角那颗地图按钮**（代码创建，不在任何布局里）→ 一次鼠标点击 = 开 / 关地图
2. 我们触摸布局里的 **map 目标**（`touch_layout_spec.json`：`{center:[width-30k, 30k], binding: MINUS}`）——
   它在游戏态被 `game_mask()` 排除（对齐 `front_ios.m:186`），所以模型**不发键**
3. 前端的 `inMinimap` 命中区（两端的**"场景名那一条"**：地图框顶部 1/4 高）

**坑在 2 与 3 的组合**：命中判定里那句"落在控件命中圆上的点归控件"把**那颗已禁用的地图键**也算进去了
→ 手指既不算点小地图、模型又不发键 → 落到世界 → 被 1 接住 → **地图被关掉**。

**规矩**：命中判定要跳过**禁用**的目标；"归控件"只对**会真的处理这一点**的控件成立。

另外：场景名那行字画在地图框**上沿之上**（框上沿 y≈3.6%，字 y≈3%），所以命中区上边界要从**屏幕顶**算起，
不能从框沿算。

## 7. 几条硬事实（省得下次再试）

- **地图框**（`dm_ui_minimap_rect`）：微缩放右 = 控件 `(−宽, 78, 宽, 718)`；`x < 0` = 从画面右边往左量；
  换算 `x0 = (x<0 ? W + x*u : x*u)`，`u = H/2160`。
- **命中区**（两端共用 `dm_ui_minimap_tap_hit`，在 `dm/host/dm_cursor.c`）：框顶那一条场景名（整宽 × 框高 1/4），
  上边界从屏幕顶算；返回 −1 = 矩形还不知道。
- **AutoMap 面板是代码创建的**（不在布局里）：`ui_panel(root,"AutoMap")`，虚表 `main+0x20c58a0`；
  可读 `+0x70/+0x74/+0x78/+0x7c`（矩形）、`+0x80`（缩放）、`+0x50`（可见位）。
- **"面板建起来了"与"地图开着"是两件事**：前者看面板对象在不在（要等），后者看可见位。
- **AutoMapMode 运行时值**（`main+0x2d479f4`）：0 全屏 / 1 微缩放左 / 2 微缩放右。
  **每个角色可能不一样**（实测见过 0/1/2），跟设置文件里的值不一定一致。
- **设置键名**：`AutomapAutoOpen`（显示名是 "AutoMap Open On Load"，别写错）；`AutoMapMode`；`AutomapFade`。
- **`AutomapAutoOpen=1` 在安卓实测不生效**（设置文件里是 1，进局地图还是关的）—— 所以安卓侧有"进局替按一次"
  这条补丁，且必须等面板建起来再按。
- **`adb push` 建出来的目录是 `shell:shell 0770`**（`/sdcard/Android/data/<包名>/` 下也是）：App（`u0_a214`）进不去。
  推覆盖层或任何 App 要读的东西，**push 完必须 `chmod -R 777`**，否则那层等于不存在（而且会让游戏 UI 初始化直接挂）。

## 8. 流程上的两条

1. **每改一步就真机复验**，日志里要能读到判别用的那一行；别攒着一堆改动一起验（这次就是攒多了，
   出问题时说不清是哪一步）。
2. **功能改动与"顺手提炼/改注释"分开提交**（比如把命中判定提到共享代码、把注释写对），
   这样出问题能干净回退。

## 9. 排查方法论：症状说「数据坏了」，先分清「读不到」还是「内容错」（2026-10-18）

**案例**：同步上游 + 重出覆盖层之后，一进游戏就 `D2Win: Fatal failure during UISystem initialization.
(Issue with missing or corrupted data?)`，后面跟一串 SIGSEGV。第一反应是"新覆盖层内容坏了"，
于是二分：去掉前端布局出一版 → 照样挂；去掉字符串表再出一版 → 还是挂。白花一小时。
真凶在**推文件的方式**：`adb push` 建出来的 `overlay/data` 属主 `shell:shell`、权限 `0770`，
App（`u0_a214`）连目录都进不去 → 覆盖层整层读不到 → UI 初始化失败。`chmod -R 777` 之后一次通过。

**为什么容易误判**：把整层覆盖层挪走、游戏就正常——这个"控制组"只证明"跟覆盖层有关"，
**证明不了是内容还是权限**。二分内容从第一步就走偏了。

**下次的检查顺序（越便宜越先做）**
1. **文件在不在、属主与权限对不对**（`ls -la`）——一条命令；推过文件之后尤其先做这个；
2. **主机侧日志**：有没有 `fs open ... 失败 errno=`；`fs 挂载` 里覆盖层挂上没有；
3. 内容是否合法（布局 JSON / 字符串表能不能解析）——比第 1 条贵；
4. 才轮到二分内容（一次只去掉一块），每次只改一个变量、只验一件事。

**一般化的规矩**：任何"文件型输入"（覆盖层、存档、设置文件、模块产物）出问题，
先把"**路径 / 权限 / 属主 / 到底有没有被读到**"排除掉，再去怀疑字节。
