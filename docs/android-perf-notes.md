## 0. 现在的状态（交接必读）

### 0.1 代码、设备、准备工作

- **代码**：本仓库（vickwv 的 fork），分支 `android-integration`。dodola 的 Android/Vulkan 层已并入。
- **设备**：小米 22081212C（骁龙 8+ Gen 1，Adreno 730 GPU），adb serial `4c6229ab`。

- **跑测试前的准备**：唤醒手机、解锁、`svc power stayon true`，游戏必须在**前台**。
  另外：`pso-cache.bin`（管线缓存文件）跨会话保留，别删。

### 0.2 现在性能是什么水平

**默认画质档（2624-075，解释见 §7.5）**，最重的营地场景（每帧约 1100 多次绘制）：

| 手机状态 | 帧率 |
|---|---|
| 温度正常（大核 2.1GHz+） | **25–27 帧** |
| 发烫降频（大核被压到 787MHz） | **19–24 帧** |

其他场景：轻中场景 37–44 帧（更早的 2168 档位数据）；菜单 60 帧（120Hz 节拍解锁之后）。

**重要背景**：这台手机现在瓶颈不在"代码有多慢"，而在**热**——手机烫了会自己降频，
帧率跟着掉。今晚实测：一晚帧率从 27 漂到 14，全部是热限造成的（详见 §7.8）。

### 0.3 翻译线程移植：做了，但这台机器没收益

上游（iPhone 版）v1.0.15 把"图形翻译"挪到了独立线程。我们移植了（代码在
`dm/android/nvn_platform_present.inc`），三轮回归稳定——但**在这台安卓机器上重场景零增益**
（大核本来就满，游戏逻辑+翻译+驱动互相挤）。结论：**默认保持同步模式**
（`DM_NVN_SYNC=1`），想要实验时用 `diagnostics/flag-nvn-queue` 打开。
移植过程中修的 3 个真 bug 保留。

### 0.4 和上游的同步状态（2026-10-17 复核）

### 0.9 按时间保存的早期实验记录

（这部分是 2026-10-16 前后的原始记录，保留原因：当时的判断依据。）

**① 管线创建卡顿（就是"进新场景卡一下"）——裁决：落盘够用，不做预热**

- 冷启动第一次遇到某条管线（显卡渲染程序）：108 条要现场编译，合计约 3 秒（单条 10-22ms）。
- 之后（热缓存）再遇到：只剩 36 条 / 146ms（几个天生就慢的大管线）。
- **结论**：管线缓存落盘已经把问题解决到可用。启动预热清单、后台编译**暂不做**（实测数据不支持）。
  已加强：缓存落盘从 30 秒提速到"改动后 5 秒内写盘 + 游戏被挂起时立刻写盘"，强杀不丢。

**② 动态 3D 分辨率（自动降分辨率保帧率）——接线完成，但实测零收益**

- 与 iPhone 版同规则：0.85/0.80/0.75/0.70 四档自动升降。
- 同局内"固定 1.0" ↔ "动态档"各跑 60 秒、来回 4 轮：**17.3 vs 17.4 帧，零差异**。
- 原因：当时场景 GPU 本来就在等 CPU，降分辨率省的是 GPU，没用。
- **定位**：动态分辨率是"GPU 余量/省电"资产，不是提帧率资产。（热包线时代可能需要重评。）

**③ 跨帧通道缓存（把渲染通道对象跨帧留着）——试过，回退**

- 当时以为每帧重建 70 个通道对象是开销大头；实测两轮无差异（而且是拿不同场景比的，无效对照）。
- 另外发现过对照组的开关根本没生效（静默失效）——这催生了"对照组必须自证"的规矩。
- **结论**：回退。（后来 2026-10-17 用正确方法重做了「持久通道/帧缓冲缓存」，见 §7.7。）

**④ 绑定计划细分（早期）**

- 每帧约 1600 次"全路径"绑定、每次 2.45µs，合计 4.0ms/帧；计划命中只占 0.3-0.6ms。
- 于是计划给 miss 加"原因计数器"——看哪个检查失败最多。结论：`state_revision`（一个版本号闸门）
  占 ~1300-1400 次/帧。这就是后来 §7.6 那个"精确校验 A/B"的起因。

**⑤ 热稳态真值（测量纪律的由来）**

- 连续玩几小时 + 充电后：~1500 次绘制/帧的场景只有 **17 帧**（冷机同场景 30+）。
- 所以：**绝对数字对比前先看热状态；跨运行对比一律用同局交替。**

**⑥ 帧循环深挖（2026-10-16 晚，五个发现)**

1. **"热数据翻案"**：有一次怀疑是热，查下来 OS 温控正常、电池 33-35°C、大核 2.3-2.75GHz——
   设备凉快时每次绘制只要 **18.8µs**（历史最佳）。那次慢的真凶是我们自己引入的 tick 回归（见 3）。
2. **翻译队列永久关闭**：同局对照：队列模式重场景 **21-29µs/绘制 vs 同步 17.5-18.4**，
   而且 GPU 等待 15-26ms/帧。机制：不是核饱和，是 GPU 反馈环（背压）上排队。**保留同步默认。**
3. **tick 回归（自己造的，已修）**：动态分辨率改成"可反复应用"后，每次系统通知都完整扫两遍
   `/proc/self/maps`（毫秒级）→ 会话慢近一倍（37.4 vs 18.8µs/绘制）。修法：指针没变化不重扫、
   5 秒才复核一次。**教训：拆保护逻辑前先看它在挡什么。**
4. **FUSE 权限坑**：shell 创建的文件默认 660——游戏进程能 stat 但读不到内容；
   `chmod 664` 立刻解决。运行时读文件的开关都必须 664。此前一次 chunk 扫描四相位全白做就是它。
5. **帧循环数据**：计划 miss 主因 = `state_revision` ~1300-1400 次/帧；tail 三段：命令缓存 1.3-1.9ms、
   状态 0.2ms、绘制本体 2.3-3.3ms；通道 begin 四段：flush 2.2-3.0ms、attach 0.13、key 1.5、begin 0.4；
   游戏线程每帧 CPU ≈ 30ms（翻译 15-18 + 游戏逻辑与录制 12-15 + 等待 ~10）。

## 1. 一帧是怎么花掉的（理解后面一切的基础）

营地场景典型一帧 ≈ 44-53ms，组成：

```
一帧时间 ≈ CPU 翻译流水（回放 ~21.5ms + 开始/结束/写回/出图 ~6ms）
         + GPU 忙时（~35-43ms，与 CPU 部分重叠）
         + 提交缝隙（GPU 空转等喂料，~8-14ms）
```

几个现象，解释为什么"小优化看不到效果"：

- 现象一：GPU 等待时间大（13-21ms）有两种可能——GPU 是墙，或者 CPU 喂得太慢。两种会交替出现，
  看场景。
- 现象二：帧率会"贴"在 60Hz vsync 的台阶上（约 50ms→20 帧、33.3ms→30 帧）。**要跨过台阶，
  帧率才会跳变**——所以小幅优化常常"看不见效果"，直到攒够跨线。这就是为什么我们既盯总帧率、
  也盯"每次绘制的微秒数"。
- 现象三：这台手机 GPU 不带宽受限（早期做 load/store 全开 DONT_CARE 测试无变化——但这个
  测试后来发现有方法论问题，见 §7.9）。真正的墙是主色通道的着色/几何本身 + 提交节奏。

## 2. 已经做成的优化（每一项：问题 → 做法 → 效果）

- **写回系统 mprotect 批量合并**：把"每次改页都单独调一次 mprotect"改成合并相邻页、一次调用。
  效果：mprotect 从 15480 次/60帧 降到 120 次，写回子系统 CPU 降 33%。（提交 `6f4235c`）
- **uniform 缓冲改动态描述符**：这类缓冲的内容跨绘制是稳定的，只是地址不同——改成"描述符固定、
  地址在绑定时动态给"。效果：描述符重建减少 85%；营地 **20.3 → 22.7 帧**。（提交 `ca12412`）
- **3D 分辨率 94012 映射移植**：和 iPhone 版同机制地改游戏内部 3D 渲染比例（默认关）。
  效果：0.8 档时 GPU 忙时减 8ms。（提交 `e683d96`）
- **出图分辨率可覆盖（`DM_GAME_RES`）**：让游戏按我们给的宽×高出图。效果：UI 和文字按原生
  清晰度出（清晰度质变）；帧率视场景小幅正负。
- **关闭遮挡查询批量**：原实现把一次"精确遮挡查询"横跨多个绘制长时间开着，在 Adreno 上会
  长期屏蔽 early-Z/HSR 优化。改正后：**营地 19.8 → 25.2 帧（+32%）**，GPU 等待 19.4 → 9.7ms。
  （注意：这与 2026-10-17 的"查询普查"结论不矛盾——那次是"完全不开查询会变慢"，
  这里是"别让一个查询长时间横跨"。）
- **120Hz 出图节拍解锁**：游戏请求的出图间隔在 60Hz 基准下会把帧率钉在 30；把基准设成 120Hz
  后上限变 60。效果：轻中场景 **37-44 帧**（原来锁 30），GPU 等待降到 ~3ms——瓶颈转为纯 CPU。
  （提交 `e46dbf4`）
- **管线缓存落盘（`pso-cache.bin`）**：原来每次启动都要从零编译管线，游玩中第一次遇到怪/特效
  会现场编译 340-571ms（"进新内容卡一下"的主因）。现在落盘复用：同类卡顿 3 个窗口 → 2 个窗口
  且持续收敛。（提交 `224c00c`）
- **BC 压缩纹理直传**：手机 GPU 原生支持 BC 压缩纹理，不需要 CPU 先解码。效果：原来首次绑定
  要解码 380-512ms（"怪物瞬移"主因之一）——现在块流直传；上传耗时 >100ms 的窗口从 9 个降到 5 个，
  同一条路线平均帧率 27.6 → 32.7；截图验证画面正确。（提交 `68852db`）
- **测试开关通道**：`diagnostics/flag-*` 一个文件一个开关，免重新编译调参数。（提交 `e683d96`）
- **持久渲染通道 + 持久帧缓冲缓存**（2026-10-17，默认开）：把渲染通道对象和帧缓冲对象跨帧
  保留，不再每帧重建。效果：CPU 每帧省 ~2-4ms（详见 §7.7）。
- **3D 画面加亮**（移植自 iOS 版）：默认开，关闭开关是 `flag-bright-k1`。
- **画质档机制**（2026-10-16）：`diagnostics/quality.txt` 一行切档，默认 2624-075（详见 §7.5）。

## 3. 试过但不行的（写下来防止重踩）

- **命令状态缓存**：跳过 68% 的重复命令，但帧率反而降——Adreno 上"重新绑定"比"比较再跳过"还便宜。
  默认关。
- **附件 load/store 全开 DONT_CARE**（全局钝刀版）：三重组合都无增益——**但这是错误的测法
  （冷机短测、只看帧率），2026-10-17 已重开，见 §7.9。**
- **分块提交粒度调参**：12/24/96 各测——无差/无差/-2.5 帧。分块实际由通道边界决定，旋钮近乎无效。
  （2026-10-17 用正确方法重扫确认 48 最优，见 §7.7。）
- **`barrier-pass-elide`**（通道内屏障省略）：±0.2 帧，噪声级。
- **`disable-wait-elision`**（关掉等待省略）：-2.3 帧 → 该机制是有价值的，保持默认开。
- **关掉 precise-sync / binding-plans**：无益或略损（这两套都是现役机制，别动）。
- **关掉 storage-bias / temp-pool / wb-stage**：灾难级（-2 ~ -18 帧）→ 都是顶梁柱机制。
- **async-drain**：-2.7 帧 → 保持关。
- **翻译队列（独立翻译线程）**：本机重场景零增益（详见 §0.3）。
- **跨帧通道缓存（早期版）**：无效对照 + 场景错配，结论作废、实现回退（后来用正确方法重做成功，
  见 §7.7）。
- **管线启动预热/后台编译**：数据不支持（冷编译总耗时 3 秒但只发生一次，落盘已解决）。
- **动态 3D 分辨率当"提帧率"用**：零差异（它是省电/省 GPU 余量的资产）。
- **绑定计划精确校验**：平局（略负），默认关（详见 §7.6）。
- **查询预重置**（消除"通道中途被打断"）：CPU 变好但帧率降 3 帧，默认关（详见 §7.7）。
- **有意通道分割器**：无增益（详见 §7.7）。
- **折叠清屏进 loadOp=CLEAR**：查下来我们的游戏根本没有"独立清屏"（清屏都是通道内直接写、
  已是优路径），方案作废（详见 §7.8）。
- **完全关掉遮挡查询**：反而更慢（-20%）——那些查询在这块 GPU 上起"有益的同步点"作用（详见 §7.8）。

## 4. 改代码前要懂的机制（速查）

- **描述符（descriptor）分类**：kind2=uniform 缓冲 / 3,9=storage 缓冲 / 4,6=纹理 / 8=驱动表 /
  10=缓冲图像。只有 kind2 走"动态偏移"（描述符固定、偏移在绑定时给）。
- **绑定计划（binding plan）**：显卡描述符的 per-shader 缓存。只对"kind2 对齐的 uniform 缓冲 +
  被采样的纹理"生效。
- **写回脏页（`nvn_dirty.c`）**：mprotect 批量认领相邻页、一次调用；有竞争的页保留 BUSY 复检。
- **出图分辨率从哪来**：游戏读 `KRES0/KRES1` 两个"参数位"（`loader.c` 装的 pthread key），
  值来自 `front_game_res`（`dm/android/diagnostics.c`）。游戏在"启动初始化"或收到"31 号通知"
  时重建输出与 3D 目标。3D 内部尺寸 = 出图尺寸 × 3D 比例。
- **3D 比例怎么应用**：`android_scale3d_tick` 写渲染器内部字段 + 调重建函数；映射锚点
  （94012）已离线验证。
- **探针**：`profile-detail` 文件开详细测量（CPU 分段 + GPU 时间戳）；`flag-pass-timing` 开
  "每个通道的 GPU 毫秒数"（开销大，只在诊断轮开）。

| Blood Moor 轻场景（3D 1.0） | 29.5* | *可能含频率加成，持续估 27-30 |

CPU 分解（详细测量轮，回放约 26.8ms 含测量开销）：绑定 9.1ms（最大块）、内存池 3.3、
描述符分配+更新 2.3、通道 begin 1.6、着色器查找 1.2、其余 ~9.3。

### 测量陷阱（重要，重复三遍级别）

- **手机凉 = 数字虚高**：静置后第一轮帧率能虚高 30-50%。一切对比先跑热，或者同局交替。
- **粒子方差**：营地火盆粒子逐帧变化，同绘制数下 GPU 负载差 ±20%。
- `PRESENT_PARTS acquire_ms` 是"每 60 帧累计"，不是每帧值。

## 6. 还没做的（按优先级，2026-10-17 更新）

1. **load/store 带宽优化重开**（§7.9）：先量省瓦数，再做带哨兵核查的精确版。
2. 动态 3D 分辨率控制器**重评**：当年零差异是 CPU 受限场景测的；热包线模式下可能反转。
3. 3D 比例档位标定：0.80/0.85 在同场景下的 ABAB 对照（补齐档位表）。
4. 测量欠账：5 分钟热机口径（取最后 30 秒）；场景判定改用游戏内存（防"菜单假读数"）。
5. 和上游隔离：`hle_oe.c` 等 6 个大改动文件的外迁（见隔离分析文档）。
6. 代码侧残余小项：绑定路径残余、PSO 键构建 memo 等（每项预期 <2%）。

**极限评估（要有的预期）**：这台手机在重场景的现实区间就是 25-35 帧（原生出图 + 3D 0.75-0.85）；
60 帧只在轻场景/静止视角可达。要全程 60，需要 Apple M 级别的 GPU。

## 7. 各轮实验的详细记录

### 7.1 世界档 × 出图尺寸：完整解剖（2026-10-16 深夜，纯离线完成）

**背景**：世界档（3D 比例 0.75）效果"世界锐度对了、用户认可"，但**界面整体缩到 0.6 倍往上飘**
（金黄血条分段宽度 117→70、节拍 131→77；整体像被乘了 0.6 再平移）。当天对 `main.patched.bin`
（打了补丁的游戏本体模块）做离线反汇编，把这条链彻底解开了。

**机制解剖（全部经反汇编核对）**：

- **出图分辨率只有两个来源**：① 启动初始化（代码地址 `0xe12d70`）② 收到"31 号通知"（性能模式
  变化）时的处理（`0xe10d30`）。两处都读 `KRES0/KRES1` 参数位，按"底座/掌机模式"选一个，
  然后走公共段：先和**全局上限 `[0x211da30]`** 比，再和**当前值 `[0x211da38]`** 比（相同就不切），
  然后触发"窗口尺寸变化"事件、写回当前值。
- **上限初值 = 1920×1080**，启动选完分辨率后会被改写成选中的值（本体 2168 / iPhone 2556）。
  **关键坑**：如果某档超过当前上限，这档会被"跳过窗口尺寸事件"。Android 保留了 1920 初值时，
  2168 / 2624 输出在启动这一步就被跳过了；iPhone 版有补丁（初值 4096×2160）所以正常送达。
  → **这就是两端启动状态不一样的根**。
- **界面画布宽度 = min(屏幕宽, 4560) 个单位**（代码地址 `0xb1a660`）；UI 的单位空间 = 屏高
  归一到 2160。屏宽超过 19:9（比如 2624×1220 = 4645 单位）会被夹到 4560（两侧各留约 26px）。
- **UI 的"屏幕宽高"用的是 3D 内部尺寸**，不是出图尺寸（界面精灵常量缓冲第 0x15 号槽 =
  [3D 内部宽, 3D 内部高, 宽高比上限]）。宽高比上限由我们的宿主按 `max(19/9, 出图宽/高)` 给。
- **运行中改出图**：游戏本体走 31 号通知；我们的端口已有完整机制，但注意——**窗口贴图是在
  启动时一次建好的，之后只能改里面的"出图区域"**。所以运行中把出图改大（如 2168→2624）会因为
  超过窗口贴图而被"出图裁剪校验"正确拦下（报 `STOP present crop bounds`，这是设计使然，不是 bug）。
  **出图增大必须从启动参数位走**（即 `DM_GAME_RES`）。
- **`w & 0x740` 掩码 bug**：编译器对 1280/1600 两档常量做了"取低 32 位"的优化，2168 & 0x740 = 64，
  会作为"窗口尺寸事件"的宽度传下去。iPhone 补丁修了它，Android 之前没修（这次修了）。

### 7.6 绑定计划"精确校验"实验（2026-10-17 凌晨）——结论：平局，默认关

**为什么试**：详细测量发现"绑定计划"（显卡描述符的 per-shader 缓存）命中率只有约 23%，
失效原因几乎全是一个"版本号闸门"（`binding_revision`，帧内变 ~1400 次）。我们猜：闸门太粗，
把本来还能用的缓存也作废了。而计划自身的校验其实已经基本完整，只差"采样器对象的身份比对"。

**怎么试**：加了一个运行中开关 `planstate.txt`（1=精确校验 / 0=粗闸门，默认 0）；精确模式下
只去掉"版本号闸门"这一项，其余检查保留，并新增采样器身份比对。

**结果**：同局 C→P→C→P 交替、按绘制归一化——**打平（精确模式略慢）**。
根因：**把闸门拿掉后会走"精细校验"，而 72% 的情况校验跑一半就发现内容是真的变了**
（每次绘制的 uniform 缓冲在内存池里换了地址是常态），不是"假失效"。多出的校验开销
≈ 省下的重建开销，收支相抵。

**结论**：默认关，代码留作杠杆（将来做"跨帧长寿命描述符"时，这个精确校验是必需品）。

**顺带的边界发现**：默认档重营地一帧 ~47ms = CPU 汇总 ~29ms + GPU 等待 ~13ms + ~8ms 空闲段
——**已经不是纯 CPU 瓶颈了**。CPU 微优化的边际收益变小。

### 7.7 通道 / 查询 / 帧缓冲三线（2026-10-17 凌晨，设备实测）

**新的浅分解测量**（默认档 2624-075 营地，每 60 帧一个窗口）：

| 项目 | 每窗口毫秒 | 说明 |
|---|---|---|
| `flush`（结束通道本身） | 0.4 | 几乎免费 |
| `chunk`（分块提交） | 156-187 | 23 次/帧 × ~110µs = **2.6-3.1ms/帧（真凶）** |
| `attach`（附件处理） | ~10 | 含附件视图创建 |
| `key`（通道键+创建） | 129（其中扫描 2.4 + 创建 129） | **40 次创建/帧 × ~54µs** |
| `begin`（vkCmdBeginRenderPass） | 25-28 | ~100 次/帧 |
| `tail`（绑定/状态/绘制本体） | 80/16/170（其中索引 28） | 绘制本体大头在驱动内部 |

**"谁在结束通道"直方图**（每帧约 101 次通道转换）：游戏换渲染目标 38 次/帧（平均每个通道
只画 1.4 个绘制！）；查询重置 35 次/帧（被打断的通道平均已画了 28 个绘制）；纹理过渡 13 次；
游戏屏障 12 次；计数器上报 3 次。

**① 查询预重置（试了 → 默认关）**：查询重置原来会在通道画到一半时中途触发（每 32 个查询一次，
约 34 次/帧），把通道打断。我们改成"帧首第一次通道转换时一次性把查询槽全部重置掉"。
- 结果：打断 34/帧 → 0；通道数 101 → 66/帧；CPU 省 2.4ms/帧……**但帧率反而从 19.2 掉到 15.8**，
  GPU 等待翻倍（834 → 2091）。换分块粒度也救不回来。
- 推测：更少更长的通道对这块 Adreno 不利（分箱 binning 的脾气）；原来的"打断"恰好充当了
  通道分割器。
- **结论：默认关。**（教训：CPU 变好 ≠ 帧率变好。）

**② 持久渲染通道缓存（默认开）**：通道对象（`VkRenderPass`）的描述是纯数据、创建后不可变，
所以可以整个会话保留。做了个哈希缓存。稳态零创建。单独收益小（通道对象本来就创建得便宜），
但让管线对象和通道句柄精确匹配，也为下一步铺垫。

**③ 持久帧缓冲 + 附件视图缓存（默认开，运行中开关 `fbcache.txt`）**：帧缓冲和它的附件视图
也跨帧保留；**纹理被释放（图像销毁）时用"代际"作废**缓存；被替换的旧对象进"退休列表"，
**只在提交围栏之后才真正销毁**（对象可能还被正在执行的命令缓冲引用——上次崩溃就栽在这里）。
- 实测：帧缓冲创建从 2400 次/窗 降到 0-19 次；创建耗时 100ms/窗 → 12；CPU 每帧省约 2ms；
  帧率无变化（当时受 GPU 限）——保留（省下的 CPU 是热预算）。
- 修正旧结论：**创建的大头是 vkCreateFramebuffer（约 54µs/次），不是 vkCreateRenderPass。**

**④ 分块提交粒度重扫**（48/96/192/0）：48 ≈ 96（24.7-24.8 帧）> 192（22.8）>>
**0（15.6 帧，灾难）**。没有"提前提交"就崩了 → **48 保持最优**；那 2.6ms/帧的提交开销是
"提前提交、和 GPU 重叠"的合理价钱。此线收口。

**⑤ 有意通道分割器**（`passsplit.txt`，默认关）：想验证"通道被切得更碎会不会更好"——
cap 24/32 ≈ 基线（~24 帧）、cap 16 在噪声内、**cap 8 明显差（19.3 帧）**。
→ 查询打断的偶然"约 32"分割已接近最优；通道结束次数存在一个平坦最优区（~80-100 次/帧）。
杠杆留档、默认关。

**⑥ 提交三段拆解**（后来补的测量）：每次分块提交里，`vkQueueSubmit` 约 1.95ms/帧
（23 次 × ~85µs，驱动内部）、`vkEndCommandBuffer` 约 0.9ms/帧——都在驱动里，无解可做。

### 7.8 GPU 侧深挖（2026-10-17 凌晨）

**方法升级（重要）**：测量窗口里新增 `SYS_FREQ` 行——记录大核当前频率、上限频率、GPU 占用率
（从手机系统文件直接读）。查询普查也接上了（每帧开了多少查询、重置多少次、上报多少次）。

**整晚帧率漂移的谜底：热限**。同一版本同一场景，帧率 27→24→21→14 全晚乱飘。接上频率监控后
一目了然：**发烫时大核被压到 787MHz、热控把上限也改到 2131MHz**（满血 3.19GHz，历史频率表
证明它跑过）；同时 GPU 渲染时间从 23ms/帧涨到 33ms/帧。**结论：这台手机现在的帧率主要由
"热包线"决定，代码侧已接近该热包线下的平衡点。**

**遮挡查询的真相（反直觉）**：每帧约 800-1050 个查询（跟着游戏"逐绘制重置计数器"的节奏走）。
**把查询全关掉反而更慢**（19.8 vs 24-26 帧，GPU 等待 571→1191）；去掉 "PRECISE" 标志没影响。
→ 这些查询在这块 GPU 上起到**有益的同步点**作用（跟"打断保护通道"同源的怪现象）。**不许优化掉。**

**GPU 每个通道花多少时间**（新维度，用 GPU 时间戳量）：总约 23ms/帧（手机凉快时）——
世界主通道 **11.4ms**（1968×915，每帧 15 个实例、327 次绘制）；同绘制量的纯深度通道 2.7ms；
2100² 阴影 1.95ms；全屏效果链 1.6+1.1ms；**UI 只要 0.78ms**；合成 0.5ms。

**"清屏折叠"候选（已否决）**：本想把独立清屏折进通道的 `loadOp=CLEAR` 省一次读写——
量了一下：**独立清屏次数 = 0**。游戏的清屏全部走"通道内直接清附件"（29 次/帧，本来就是
最优路径）。方案作废。（先量后做，避免了白干。）

### 7.9 上游建议对照 + 三项修正（2026-10-17）

上游 iPhone 版作者在 issue 里给了他们的性能经验清单（`jhaizhou-ops/d2r-mobile#59`）。
逐条对照后，**我们认了一个最大的错**：

| 他们的建议 | 我们的状态 | 判定 |
|---|---|---|
| 同步上游 v1.0.15/16/17 | 都已合入；翻译线程本机零增益；动态比例默认关 | ✅ |
| **分块 GPU 带宽四招**（loadOp DONT_CARE / storeOp DONT_CARE / 清屏并入 CLEAR / 合并通道） | 我们早期判"无效" | ❌ **测法错了**：冷机短测 + 只看帧率 + 全局钝刀。人家实测这是省带宽头号项（附件读写 506→226MB/帧）。**已重开** |
| 管线：落盘✅ + 启动预热 + 后台编译 | 预热未做 | ⚠️（残余=首次遇新内容 146ms 级） |
| 测量：交替✅ / 热机取末30秒 / 掉帧口径 / 用游戏内存判场景 / 校验层关 | 后两项欠账 | ⚠️ |
| 60fps 出图节拍解锁 | 已做（120Hz） | ✅ |

**三项修正行动（已启动）**：
1. **load/store 带宽重开**：先用"钝刀模式 0↔2 交替 + 3 分钟热机相位 + 主指标=电池电流（瓦数）"
   量出上限收益（正在跑）；如果省瓦明显，再做精确版——精确版顺序：storeOp DONT_CARE（写后没人读的）
   → loadOp DONT_CARE（首绘全覆盖的，需哨兵证明）→ 清屏并入。**哨兵核查**：把画面清成特殊值 →
   跑 → 读回来数残留像素；并且要先用一个故意做错的例子证明"核查真的能报警"。
2. **动态分辨率重评**：当年的"零差异"是 CPU 受限场景测的，现在热包线模式可能反转。
3. **测量欠账**：长热机口径（≥5 分钟、取最后 30 秒）；场景判定改读游戏内存。
