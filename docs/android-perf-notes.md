# Android 性能工程笔记（骁龙 8+ Gen 1 / Adreno 730）

## 0. 会话交接（压缩现状，2026-10-16）

**代码位置**：本仓库（vickwv/d2r-mobile fork）分支 `android-integration`；dodola 的 Android 层已并入。
**设备**：小米 22081212C（骁龙 8+ Gen 1 / Adreno 730，serial 4c6229ab）。当前开关：
`diagnostics/` 下 `flag-gameres-native`、`flag-present-hz-120`；`pso-cache.bin` 跨会话持久；
跑测前：`input keyevent KEYCODE_WAKEUP; svc power stayon true`，必须解锁+前台。

**真实性能现状**（热稳态，原生 2168×1220 出图）：轻中场景 31–44fps、重营地 24–28、
用户 14 分钟真实游玩均 36.2fps；菜单 60（120Hz 节拍解锁后）。GPU 等待通常只剩 3–10ms/帧
——**瓶颈是 CPU 翻译流水**（replay ~15–22ms，其中描述符绑定 ~6.6ms、renderpass ~3.5ms）。

**本轮（会话末尾）结论——翻译线程移植**：
Apple v1.0.15 的翻译队列（游戏线程只入队、nvn-translate 线程翻译/出图）已移植进
`dm/android/nvn_platform_present.inc`（+ 同步等待接队列、释放/改注册等待发布）。三轮回归稳定，
但本 SoC **重场景零增益**（大核已饱和：游戏逻辑+翻译+驱动），菜单 60 同步模式本来就有。
→ 默认同步（`DM_NVN_SYNC=1` 由 app_jni 设），`diagnostics/flag-nvn-queue` 可实验开启。
三处真 bug 修复保留（对同步模式亦更稳健）。

**上游同步**：只落后 2 个提交，已合（v1.0.17 存档数据损失修复 `9de307e` + Mac 修复）。
owner（上游作者）给 dodola 的建议六条：①同步上游 ✅ ②翻译线程 ✅（已移植，本机无增益）
③load/store 带宽——本机实测**无 fps 增益**（非带宽瓶颈），含哨兵核查法留作省电实验
④管线缓存 ✅（落盘持久化；预热/后台编译未做）⑤测量方法论——采纳中（见 §7）
⑥D2R 逻辑固定 25 拍、出图节拍独立 → 我们的 120Hz 节拍解锁**速度安全**（owner 证实）。

**下一步队列**（优先级序）：
1. 测量基建：上屏时刻（`mtl_presented_time` 空桩）接线 + 热机尾 30s 口径 + 良品/弃品判定
   （游戏内存场景检测优于截图）；Apple 侧已有 `DM_NVN_UB` 交替测量可参照移植。
2. 管线预热：启动期按常用清单预建（iOS 清单 397 行实证）+ 后台线程编译。

4. load/store 哨兵协议实测化（省瓦数，热机频率受益）。

**跨帧渲染通道缓存（已试 → 已回退）**：
- 根因怀疑：通道/帧缓冲每次提交销毁重建、每帧约 70 个附件组合 → 曾以为 70 次真创建是 renderpass 桶的大头。
- 实测：A/B 两轮 renderpass_ms 无差（192/201 vs 181/198/窗口，±3% 噪声）；且对照组的 flag 可能根本没生效
  （同机制的 `flag-resource-stats` 无输出）——跨 run 还有场景错配（A 尾部 124k draws vs B 66k）与热差。
- **裁决：实现回退**（Adreno 的 vkCreateRenderPass 近乎免费；桶里的大头在 render_at 的其它部分）。**方法论升级：
  以后所有 A/B 一律进程内交替**（比例/load-store 的运行时开关已建好）。

### §0e 动态比例 进程内交替 A/B 裁决（2026-10-16 晚）

同局内 `1.0 ↔ 动态档` 各 60 秒 ×4 轮、每相跳过切换后 25 秒取稳态（平均 draws 92728 vs 92899，场景可比）：

| 相位 | fps 均值/中位 | p10 |
|---|---|---|
| 画质 1.0 | 17.3 / 17.3 | 16.7 |
| 动态 ≤0.70 | **17.4 / 17.2** | 16.7 |

**零差异**。原因：热稳态下 `gpu_wait≈0`、纯 CPU 受限——降比例省的是 GPU 的活，GPU 本就在等 CPU。
**定位：动态比例 = GPU 余量/功耗资产，不是 fps 资产**（等 CPU 削减完成、GPU 变瓶颈后才值钱）。
渠道：`flag-3d-scale-dyn`（默认关）、`flag-3d-floor-85/80/75`、`flag-3d-quality`（A/B 切换）。

### bind 桶细分（`RENDER_BIND_SPLIT`，热稳态 17fps 档）

- 全路径调用 ~1600 次/帧、2.45µs/次 = **4.0ms/帧**；绑定计划命中 ~1000-2000 次/帧、~0.3µs/次 = 0.3-0.6ms。
- bind 桶合计 5.4-6.0ms/帧 ✓（细分+prep 对齐）。
- 下一步：给计划 miss 加**原因计数器**（哪个校验失败最多：epoch/state_revision/registry/pool/逐资源），对症提高命中率。

### 热稳态真值（测量纪律）

- 连测数小时+充电后：**~1500 绘图/帧场景 ≈ 17fps**（冷机同场景 30+）；整帧 59ms 中翻译侧 ~18-20ms，
  其余是节流后的游戏逻辑+录制。**绝对数字对比前先看热状态**，跨 run 对比一律用进程内交替。

### 2026-10-16 晚：帧循环深挖 + 三个大发现

**① 热数据翻案**：OS 温控 NONE、电池 33-35°C、大核 2.3-2.75GHz——设备凉时每绘制 **18.8µs**（历史最佳）。
慢会话的真凶是 **tick 回归**（见③），不是热。

**② 队列永久关闭**：S1/Q2 完整对照 + 现场数据——队列重场景 **21-29µs/绘制 vs 同步 17.5-18.4µs**、`gpu_wait`
15-26ms/帧（翻译线程在 GPU 背压上排队）。机制清楚：不是核饱和，是 GPU 反馈环。**保留同步默认。**

**③ 我引入的 tick 回归（已修）**：动态比例"可反复应用"改造去掉了原来的一次性闸门 → 每次通知轮询
都扫两遍 `/proc/self/maps`（毫秒级）→ 武装态会话被拖慢近一倍（37.4 vs 18.8µs/绘制）。修法：
校验缓存化（只在指针变化或每 5 秒复核）。**教训：去掉守恒闸门前先看它挡住了什么。**

**④ FUSE 读权限坑（重要）**：shell 创建的文件默认 `-rw-rw----`(660)——app 能 **stat**（所以 flag 通道
一直正常）但 **fopen 读不到**；`chmod 664` 后立刻可读。运行时读文件的开关（chunkd.txt/loadstore.txt）
**必须 chmod 664**。此前一次 chunk 扫描因此整体无效（四相位实际都是默认值）。

**⑤ 帧循环仪表数据（profile-detail 下、热稳态）**：
- 计划 miss 主因 = **state_revision ~1300-1400 次/帧**（资源校验根本没机会跑）→ 全路径 1600 次/帧；
  放宽方案需补齐校验缺口（采样器身份/写标志）→ 专门工程
- tail 三段：bind 1.3-1.9 · state 0.2 · **draw 2.3-3.3ms**（索引+绘制+遮挡结算）
- render_begin 四段：**flush 2.2-3.0ms**（含 pass_end + sub_chunk_flush）· attach 0.13 · key 1.5 · begin 0.4
- **游戏线程每帧 CPU ≈ 30ms**（翻译 ~15-18 + 游戏逻辑+HLE 记录 ~12-15 + 等 ~10）——新探针
  `游戏线程每帧 CPU`（/proc/thread-self，每 60 帧一行）

## 1. 帧模型（理解一切优化的基础）

营地场景典型帧 ≈ 44–53ms：

```
帧时间 ≈ CPU 翻译流水(replay ~21.5ms + begin/retire/wb/present ~6ms)
       + GPU 忙时(~35–43ms, 与 CPU 部分重叠)
       + 提交缝隙(gap ~8–14ms, GPU 空转 = 喂料不及)
```

- 现象一：`gpu_wait` 大（13–21ms）→ GPU 是墙或 CPU 喂不及（两者交替出现，看场景）。
- 现象二：帧率贴 60Hz vsync 台阶（≈50ms→20fps / 33.3ms→30fps）。**跨过台阶才有 fps 跳变**，
  所以小幅优化有时"看不到效果"直到累积跨线。
- 现象三：S8G1 上 **GPU 不带宽受限**（load/store DONT_CARE 全开无变化），
  墙是主色 pass 的着色/几何本身 + 提交节奏。

## 4. 关键机制速查（改代码前必读）

- **描述符**：kind2=UBO / 3,9=SSBO / 4,6=纹理 / 8=驱动表 / 10=缓冲图像。动态偏移只打 kind2；
  快照/临时路径自动回落 dyn=0；>4G 偏移回落快照（实际不会发生）。
- **绑定计划**（binding_plan_*）：只对 kind2-aligned + 采样纹理生效；动态绑定后偏移不再作废计划。
- **写回脏页**（nvn_dirty.c）：`prep_write` 批量认领相邻页 + 单次 mprotect；竞争页保留 BUSY 复检。
- **出图分辨率**：游戏读 KRES0/KRES1 线程槽（`loader.c` 装的 pthread key），值来自
  `front_game_res`（`dm/android/diagnostics.c`，现支持 `DM_GAME_RES=WxH`）；
  游戏收到 31 号通知或启动初始化时重建输出与 3D 目标（3D 内部 = 输出 × 3D 比例）。
- **3D 比例**：`android_scale3d_tick`（TryPopMsg 内调用）写渲染器 +0x66a4 并调 resize；
  94012 映射锚点已离线验证；一次性生效后靠游戏自身重建沿用。
- **探针**：`profile-detail` 开 GPU 时间戳（SEG gpu_busy）与 `RENDER_CPU_PROFILE` 分解；
  `flag-pass-timing` 开逐 pass GPU 毫秒（PASS_TIME rank 行）；开销大，只在诊断轮开。

### 测量陷阱（重要！）

- **冷却频率加成**：设备静置后第一轮帧率可虚高 30–50%（28.9 vs 19.2 同配置）。
  一切对比必须"先烧机一轮，再 A/B"，或交替多轮取趋势。
- **场景粒子方差**：营地火盆火焰/粒子逐帧变化，同 draws 数下 GPU 负载可差 ±20%。
- `PRESENT_PARTS acquire_ms` 是**每 60 帧累计**，每帧约 0.1ms，不是每帧值。
