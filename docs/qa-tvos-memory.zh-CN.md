# tvOS 内存优化与场景切换观察（2026-10-18）

[English](qa-tvos-memory.md) | **简体中文**

两轮优化延长了实测游玩时间，均衡版在短时窗口恢复到接近 60 FPS，但**回城、返回洞穴和一键重开仍未全部稳定**。本记录用于评审实验补丁，不是稳定性验收。以下只保留脱敏的数值和宿主日志片段；完整设备日志留在本地。

## 环境与口径

- Apple TV 4K 第三代，A15、4 GB，tvOS 27.0；已部署老机型 ASTC 补充包，保留动态分辨率，初始比例 0.75。
- Mac M4，macOS 27.0.1，Xcode 27.1；游戏版本 3.3.94012。
- 真机记录来自基于 `1784563` 的本地开发版本。提交前同步上游 `9393b00` 并重新跑宿主与针对性图形测试；最终整合版尚未重新完成真机回归。
- footprint、内核记录峰值与 `os_proc_available_memory()` 余量均以 MiB 记录。Metal 分配、游戏堆容量与进程 footprint 是不同口径，不能相加。设备有 4 GB 不代表 App 能占用全部内存。

## 第一轮：积极回收只读上传缓存

第一轮每 60 帧检查一次，保护最近 120 帧使用的纹理，软预算 384 MiB；余量低于 256 MiB 时尝试回收至少 64 MiB，一批最多目标 128 MiB。GPU 写过的纹理不回收；缓存引用交给已有 GPU fence 延迟释放。回收同时清除描述符别名并使参数缓冲缓存失效，避免继续使用旧 GPU 句柄。

用户反馈游玩时间延长，观察期间未再退出，但卡顿明显。日志出现频繁的小批次回收：

```text
tvOS 贴图缓存：回收 6 张 26 MB（等待 GPU fence），缓存 205 → 179 MB，系统余量 173 MB
tvOS 贴图缓存：回收 2 张 0 MB（等待 GPU fence），缓存 181 → 180 MB，系统余量 193 MB
```

日志中的 MB 是整数 MiB，0 不代表完全没有回收。该轮还开启过 `DM_RES_CHECK`、驻留普查，且有温控状态 2；绑定热路径的诊断加锁会影响性能。因此，不能将全部帧率下降归因于回收，也不能与后续冷机短测作严格 A/B 对比。

## 第二轮：保留 ASTC，降低回收频率

最终补丁包含以下均衡策略：

| 策略 | 普通情况 | 紧急情况（余量 <96 MiB） |
|---|---|---|
| 扫描间隔下限 | 3 秒 | 1 秒 |
| 最近使用保护 | 600 帧 | 120 帧 |
| 每批回收目标 / 目标上限 | 压力下至少 16 / 最多 32 MiB | 64 / 64 MiB |
| 小批次 | 冷数据不足 4 MiB 时跳过 | 不跳过 |

低于 160 MiB 进入压力模式，恢复到 224 MiB 才退出；软预算仍为 384 MiB。单张纹理不可分割，实际回收可超过目标；活跃和 GPU 写入资源受到保护，缓存仍可能超过软预算。这不是进程内存上限保证。

对于首次写入、格式与块边界兼容的 BC3 2D/数组目标，直接保留补充包来源的 ASTC 块。后续遇到不兼容拷贝、缓冲写入、清除或附件写入时，逐 mip/层保留内容再回退 RGBA。日志确实观察到一个 `128x128`、42 层、1344 KiB 的压缩数组分配；尚无证据证明这项优化显著降低了整个进程的峰值，回退路径也仍需更多真机覆盖。

取消 `DM_RES_CHECK` 和驻留普查后的短测记录：

| 启动后秒数 | 温控状态 | 3D 比例 | 上屏 FPS |
|---|---|---|---|
| 10 | 0 | 0.75 | 58.9 |
| 20 | 0 | 0.75 | 59.9 |
| 30 | 0 | 0.75 | 59.9 |

这只是短时性能窗口，不能推导长期帧率或切图稳定性。`DM_TV_TEXTURE_CACHE_MB=0` 可关闭回收；`DM_TV_ASTC_ARRAYS=0` 可关闭 ASTC 保留，供后续受控对照。

## 回城、一键重开和返回洞穴

定位到一个独立的宿主引用问题：`TextureFinalize` 原先只删除 serial 表项，描述符缓存仍持有旧纹理/视图，直到相应槽重新注册。补丁撤下所有匹配别名，保留客体描述符快照，使参数缓冲缓存失效，并继续按原有 GPU fence 保留在途引用。此修复作用于共享 Metal 后端，不能仅靠 tvOS 观测替代其他平台回归。

| 用例 / 阶段 | 证据 | 结论 |
|---|---|---|
| 原始版本游玩约 6.5 分钟 | 系统 Jetsam 报告：`DmTV`，`reason=per-process-limit`，`rpages=134446`，页大小 16384 字节，即约 2100.72 MiB 常驻页 | 此次退出确认触发进程内存上限；常驻页口径不等于 footprint |
| 均衡版一键重开，引用修复前 | 原版保存退出、前端载入、202 ms 进入读取画面；随后 `signal 9`；最后低频样本 1991 MiB，余量 106 MiB，温控 0 | 已复现退出，未取得对应新 Jetsam，终止原因未最终确认 |
| 引用修复后一键重开 | 1919 ms 进局并核对同一角色成功 | 一次通过；随后另一轮仍出现 `signal 9`，最后低频样本 1932 MiB / 余量 165 MiB |
| 洞穴 → 城镇，引用修复及观察日志开启 | 宿主区域 8 → 1，用户确认成功；当时 2644 个采样，内核记录峰值 2074 MiB、最低采样余量 46 MiB | 一次通过，内存余量仍很小 |
| 同一观察轮，城镇 → 洞穴 | 用户报告再次退出；宿主区域 1 → 8 后 `signal 9`；取回 6015 个采样，末样本在 622668 ms，footprint 2054 MiB、内核记录峰值 2086 MiB、余量 43 MiB | 新增失败方向；仍未取得对应新 Jetsam，不能单凭 signal 9 宣称根因 |

最新退出前的连续采样摘录，列名均来自设备采样器，MiB 向下取整：

```text
elapsed_ms  footprint_MiB  peak_MiB  headroom_MiB  GPU_MiB
622462      1963           2074      134           2076
622568      2035           2074      62            2135
622668      2054           2086      43            2185
```

这说明加载时余量迅速下降；约 100 ms 的采样仍可能漏掉更短的 footprint 峰值。温控状态 2 在这轮也出现过，不能用温控状态或最后一条内存样本单独判定退出原因。原始一次 Jetsam 已证实内存限制，后续退出仍需系统报告确认。

## 观察与验证

临时设置 `DM_TV_MEM_TRACE=1`，每约 100 ms 将内存写入设备 `Caches/D2R/memory-trace.tsv`，最多 18000 次采样；每次写后刷新，下次启用会覆盖。退出后先取回记录再重启。配合 `DM_RES_CENSUS=1` 可打印大纹理格式分组；正常性能测试均关闭这两项及 `DM_RES_CHECK`。

已完成：宿主全套 `make -C dm/host/tests run`，以及 `t_pkg_cache`；Metal API Validation 下 `t_tex_finalize` 11 项、`t_rt_srgb_view` 14 项、`t_nvn` 75 项均 0 失败；文字检查通过。开发阶段 tvOS 签名构建成功。同步上游后再次通过宿主全套及上述针对性图形测试。

图形全套 `make -C dm/gfx/tests run` 在本地 `t_refl` 的 85 项中有 2 项失败（绑定反射期望），该测试不链接本次修改的 `nvn_mtl.m`；没有宣称图形全套通过。iOS 构建、iOS 测试、改写等价回归与 Mac 冒烟未在本轮重新运行。

后续验收：多次双向洞穴往返、连续一键重开、长时间战斗、混合 ASTC/普通 BC 写入与回退画面核对、其他平台共享引用生命周期回归，以及诊断关闭、相同温控/场景下的帧率对照。当前应保留为草稿。
